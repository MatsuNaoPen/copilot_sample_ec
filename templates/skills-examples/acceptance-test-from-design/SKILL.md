# 受入テスト項目作成 skill

設計書 `docs/design.md`（および要件定義書 `docs/requirements.md`）の **受け入れ条件・テスト観点**を、
人手で実施・サインオフできる **受入テスト項目書 `docs/acceptance_test.md`** に落とす手順書。

## 立ち位置（重要：自動テストとの違い）
- **これは「人が実施・記録する受入テスト仕様（チェックリスト）」を作る skill。**
  ID・前提/入力・操作・**具体的な期待結果**・対応要件・結果欄を持つ表を起こす。
- 一方 `tests-from-design`（プロンプト）は **Vitest の自動テスト `src/pricing.test.ts`** を生成する別工程。
  両者は補完関係（同じ受け入れ条件を、自動と手動の両面から担保する）。混同しない。
- 観点（正常系・境界値・異常系）は両者で揃える。本 skill の表は **要件の受け入れ条件と一対一でたどれる**ようにする。

## 入力
| 役割 | パス |
|------|------|
| 主入力（公開IF・テスト観点） | `docs/design.md` |
| 受け入れ条件・業務ルール | `docs/requirements.md` |
| 出力の構成（踏襲する） | `docs/templates/acceptance_test_template.md` |
| プロジェクト規約 | `.github/copilot-instructions.md` |

**出力**: `docs/acceptance_test.md`

> `docs/design.md` が無ければ作成できない。`tdd-demo` skill のステージ1→2（要件定義→設計）で
> 先に生成するよう案内して終了する。`docs/requirements.md` もトレーサビリティに使うため参照する。

## 手順
1. 入力ファイルを読み込む（`docs/design.md` が無ければ生成を案内して終了）。
2. テンプレート `acceptance_test_template.md` の構成に沿って `docs/acceptance_test.md` を新規作成する。
3. 設計のテスト観点・要件の受け入れ条件を、下記「網羅する観点」に従い **1観点＝1項目以上**で表に展開する。
4. §3 トレーサビリティ表で、各受け入れ条件が最低1つの項目IDで確認されることを保証する（取りこぼしゼロ）。
5. 完成後、**カバーした受け入れ条件の件数と、未カバー/保留があればそれ**を1〜2行で報告する。

## 網羅する観点（要件の受け入れ条件に対応）
`tests-from-design` と同じ観点を、**手動実施できる具体値**で起こす。

### 正常系
- 会員割引が効く（セール品を除いた小計に 10%・`Math.floor` 切り捨て）
- クーポンが効く（固定 500円引き）
- セール品が会員割引の対象外になる
- 送料無料になるケースと、送料がかかるケースの両方

### 境界値
- 割引後 **ちょうど 5,000円 → 送料無料**
- 割引後 **4,999円 → 送料 500円**
- 会員割引で端数が出るケース → 切り捨て（例: 2,999円の10%＝299.9→**299円**）

### 異常系
- 数量が 0 以下 → `PricingError`
- 単価がマイナス → `PricingError`
- 存在しないクーポンコード → `PricingError`
- 会員割引とクーポンの併用指定 → `PricingError`
- 空カート → **合計 0円・送料 0円**（これはエラーではなく 0 を返す）

## 書き方の指針
- **期待結果は具体値で書く**。「正しく計算される」は不可。
  入力（単価×数量・セール品か・会員フラグ・クーポン）から、小計 → 割引 → 割引後小計 → 送料 → 合計を
  順に計算し、最終的な数値を記す。異常系は送出される例外名（`PricingError`）を記す。
- 各項目に **区分（正常系/境界値/異常系）** と **対応要件**（§3 と対応づけ）を必ず付ける。
- 入力は再現可能な粒度で。例: 「単価1,000×数量2（非セール）＋単価2,000×数量1（セール）／会員ON／クーポンなし」。
- 結果欄は **未実施（空）** にしておく（実施時に Pass/Fail/Blocked を記入する運用）。
- ID は連番（AT-001…）。観点を増やすときは行を追加する。

## 守ること
- **設計書・要件定義書に無い仕様を勝手に作らない。** 期待値は必ず設計の業務ルールから導く。
- **端数処理が要件/設計で未決（不明点・要確認）なら、期待値はその決定に依存する。**
  勝手に確定させず、該当項目の備考に「端数処理の決定待ち（切り捨て前提で仮置き）」と明記し、
  決定後に確定する旨を残す（規約上は `Math.floor` 切り捨てが既定）。
- **すべての受け入れ条件を最低1項目でカバー**する。漏れがあれば §3 で可視化し報告する。
- 入力に使った `docs/design.md` / `docs/requirements.md` は**書き換えない**（参照のみ）。

## 補足（xlsx で配布したい場合）
表ベースのため、`docs-xlsx` skill で xlsx 化できる:

```sh
python3 scripts/docs_xlsx.py export docs/acceptance_test.md docs/acceptance_test.xlsx
```

## 完了の定義
- `docs/acceptance_test.md` がテンプレート構成で作成され、正常系・境界値・異常系を網羅している。
- 各項目に区分・具体的な期待結果・対応要件・（未記入の）結果欄がある。
- §3 トレーサビリティで全受け入れ条件がいずれかの項目に対応づいている。
- 端数処理など未決事項は確定させず、備考に保留として明示している。
